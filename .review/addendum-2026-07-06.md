## REVIEW ADDENDUM (survey pass, 2026-07-06)

### CONTEXT

- Codebase: hyperion — R package (S7/S3 display + metadata layer) over a Rust
  extendr backend (workspace crates `core`, `nonmem`, `scheduler`) wrapping
  four pharos git crates; companion to the `pharos` CLI for NONMEM
  pharmaceutical model development: read/check/copy models, submit to
  SLURM/SGE, summarize runs, extract parameter estimates/metadata, model
  lineage.
- Primary consumers: pharmacometricians / internal data scientists using it
  interactively in R and inside Quarto/R Markdown reports; outputs feed
  scientific reporting, so silently-wrong numbers or labels are the
  worst-case failure.
- Known constraints or intentional decisions worth flagging up front: pharos
  owns all NONMEM comment parsing — R has no fallback parsers and `NA` names
  are acceptable output (maintainer instruction); pharos crates track
  `branch = "main"` with Cargo.lock as the effective pin and a daily CI
  drift tripwire `[Q3]`; testthat snapshot files are maintainer-owned and
  must never be edited by tooling.
- Areas of specific concern: correctness of parameter identity/ordering in
  user-facing tables AND robustness of the submission/config workflow —
  maintainer weights these equally `[Q7]`; panic behavior at the R↔Rust
  boundary; output-file path resolution conventions duplicated between R and
  Rust. Primary deployment target is Linux clusters `[Q8]`.

### PRIORITY TARGETS

Allocate roughly 80% of review effort here, as hypotheses to confirm or
refute.

**T1. Parameter identity/ordering implemented ≥4 times, with
maintainer-confirmed drift.** Canonical ordering is THETA < OMEGA < SIGMA
`[Q1]`; `src/rust/nonmem/src/model/summary.rs:80-97` (THETA < SIGMA < OMEGA)
is confirmed wrong and `src/rust/nonmem/src/model/parameters.rs:26-60` is the
correct convention; both hand-parse `NAME(i,j)` indices — review both for
further drift and for what the summary.rs deviation has been silently doing
to summary output ordering. R re-walks
omega/sigma block structure with a manual `param_idx` including BlockSame
back-search (`R/model-methods.R:510-606`), and R resolves parameter names two
different ways (`find_parameter`, `R/comments-classes.R:347-419` vs
`resolve_comment`, `R/comments-query.R:56-105`). Investigate: which ordering
the .ext/.shk join in `get_parameters` (parameters.rs:103-200) actually
requires; trace name alignment for models with non-contiguous omega diagonals
and BlockSame (`inst/extdata/mod/everything.mod`, `iov.mod`); compare
`find_parameter` vs `resolve_comment` semantics on identical queries; check
`get_eta_labels` (`R/comments-query.R:291-334`) sequence-position vs
row-index labeling. `[Q1]`

**T2. Panic policy at the extendr boundary.** `.onLoad` installs an empty
panic hook (`src/rust/core/src/lib.rs:58-61`; `R/zzz.R:3`); R comments claim
panics abort the session and guard with `file.exists()` pre-flights
(`R/model-methods.R:119-170`); panic paths remain reachable from exported
functions (`nonmem/src/model/comment_info.rs:125,137` `panic!`;
`nonmem/src/output_files/ext.rs:95` `unwrap()` on `table.method`).
Investigate: what extendr 0.9 actually does on unwind; exercise
`read_ext_file` on an ext table with no method line and
`get_model_comment_info` on mismatched comments; state the de facto policy
and which guards are load-bearing. `[Q2]`

**T3. Output-file location split R/Rust; `$EST FILE=` honored only on the
Rust path.** Rust `resolve_ext_path` honors `$EST FILE=`
(`src/rust/nonmem/src/utils.rs:206-211`); R `build_running_summary`
re-derives `{dir}/{stem}/{stem}.ext|.grd` by naive convention
(`R/model-methods.R:119-170`); `copy_model` re-implements ext resolution
inline and takes its `to` path raw from CWD while other paths are
config-relative (`src/rust/nonmem/src/model/copy.rs:165-196`;
`utils.rs:274-301`). Investigate: `summary()` on a running model using
`$EST FILE=`; grep all R-side `file.path(dirname(...), base_name, ...)`
constructions and map each to its Rust counterpart; canonicalize-failure
fallbacks in `to_config_relative`/`from_config_relative`
(utils.rs:279-301); `copy_model` from a subdirectory. `[Q4]`

**T4. Hand-rolled .ext parsing silent-wrong-data modes (zero tests).**
Hardcoded sentinel codes -1000000006/-1000000001 handled only when both rows
present (`src/rust/nonmem/src/output_files/ext.rs:182-221`); final-estimate
rows selected by string prefix "-1000000000" (ext.rs:294);
`get_final_estimates` takes names from the first file and silently tolerates
row-length mismatches (ext.rs:343-376). Investigate against shipped exotic
fixtures (`inst/extdata/ext/itsimp.ext`, `bql.ext`, `saemimp.lst`), missing
sentinel-row combinations, heterogeneous multi-model scans; check the shk
join in `get_parameters` and the eta/eps near-duplication
(`shk.rs:57-218`) for the same class of positional assumptions. `[Q10]`

**T5. Test coverage anti-correlated with risk; Rust tests never run in CI.**
No test invokes `copy_model`, `init`, `check_model`, `submit_model_to_*`,
`set/update/clear_metadata_file`, or `use_comments`; ext/grd/shk/transforms/
summary/parameters Rust modules have zero tests; `#[test]`s that do exist
(`utils.rs`, `run_status.rs`, `slurm.rs`) are not executed by
`.github/workflows/R-CMD-check.yaml` or lefthook. Investigate the coverage
map's accuracy and identify the cheapest high-value seams (copy_model
round-trip in tmpdir, metadata write/clear round-trip, ext parsing unit
tests, a `cargo test` CI step). The NMTRAN/cluster boundary itself is
accepted as untestable in CI. `[Q5]`

### OPEN HUNT

This survey spent the least time on — counter these blind spots in the ~20%
sweep:

- Config plumbing failure modes: three loaders in
  `src/rust/nonmem/src/utils.rs` (`get_comment_type` silently None on any
  failure, `load_nonmem_config` CWD fallback, `get_pharos_config` discarding
  most of the config with thresholds also defaulted R-side in
  `R/summary-methods.R:6-26`), plus the string-sentinel error channel from
  `find_pharos_config_file` (`core/src/lib.rs:64-74` grepped at
  `R/utils.R:563`, `R/pharos-config.R:20`).
- Metadata JSON write paths (`src/rust/nonmem/src/model/metadata.rs`) —
  read-modify-write behavior, partial writes, concurrent-ish usage from
  multiple R sessions.
- `transforms.rs` numerical correctness (CV/CI/RSE formulas per transform
  type, manual R-style recycling, `src/rust/nonmem/src/output_files/transforms.rs`).
- Scheduler submit paths (`src/rust/scheduler/src/lib.rs`) — env/arg
  construction, `which("pharos")` failure modes, error surfacing after
  submission. (Partition-validation asymmetry itself is known-intentional,
  see below `[Q6]`.)
- Lineage correctness (`src/rust/nonmem/src/model/lineage.rs`
  `filter_lineage` mutating `LineageTree::default()` pub fields, 200-217) and
  the R tree-rendering regex-on-rendered-output pattern
  (`R/tree-methods.R:96,171,390`).
- Vignettes (`vignettes/*.Rmd`) and roxygen docs vs actual behavior — not
  read at all in the survey.
- Windows build scaffolding (configure.win, `src/Makevars.win.in`,
  `src/conjurer-win.def`): Windows is not fully supported `[Q8]` — review
  only for rot/misleading-signal risk (scaffolding implying support that
  doesn't exist), not for Windows-specific correctness.

### KNOWN-INTENTIONAL / OUT OF SCOPE

- Pharos owns all comment parsing; no R-side fallback parsing exists by
  design, and `NA` parameter names are acceptable when pharos cannot parse a
  comment — do not flag NA-name tolerance or the absence of R-side parsers.
  (Source: maintainer instruction; also NEWS.md 0.5.0 "R-side raw comment
  parsing is removed. All comment parsing is owned by pharos.")
- testthat snapshot files (`tests/testthat/_snaps/`) are maintainer-owned;
  never propose editing them as a fix. (Source: maintainer instruction.)
- pharos crates tracked at `branch = "main"` is the active co-development
  workflow, with Cargo.lock shipped (`Config/build/extra-sources`) as the
  pin and `pharos-dependency-check.yaml` as a deliberate daily drift
  tripwire — do not flag branch-tracking itself; reproducibility edge cases
  (dead vendor tree, token-less source builds) remain in scope. `[Q3]`
  (Source: maintainer answer confirming; workflow file + README badge.)
- SGE submission has no partition validation because SGE does not support
  partition selection — do not flag the SLURM/SGE partition-validation
  asymmetry as a gap. `[Q6]` (Source: maintainer answer.)
- Windows is not fully supported; the primary target is Linux clusters — do
  not report Windows-specific correctness findings. Scaffolding-rot or
  support-signaling confusion may still be noted. `[Q8]` (Source: maintainer
  answer.)
- `tests/testthat/setup-config-dir.R` pins `hyperion.config_dir` to the
  install root specifically because pharos's CWD-walk would otherwise find
  the wrong pharos.toml during tests — the option's existence is deliberate,
  documented in that file's comments. (Source: in-repo comment.)
- `R/tree-methods.R:291-296` deliberately drops `based_on` edges that point
  outside a lineage slice (documented in comment) — not a bug. (Source:
  in-repo comment.)

### REPO MAP

(Section 1 of `.review/survey-2026-07-06.md`, verbatim; `(?)` marks items to
re-verify rather than trust.)

**Purpose.** hyperion is an R package companion to the `pharos` CLI for
pharmaceutical (NONMEM) model development: read/validate/copy models, submit
them to SLURM/SGE clusters, summarize runs, extract parameter estimates and
structured parameter metadata, and track model lineage. Codebase type: **R
library (S7/S3) over a Rust staticlib backend (extendr)**, which itself wraps
four pharos git crates. First supported modeling software is NONMEM.

**Entry points.**
- No mains/routes. Public surface = ~60 R exports (`NAMESPACE`), of which 37
  are thin `.Call` wrappers generated into `R/extendr-wrappers.R` at build time
  by `src/rust/document.rs`.
- Rust `#[extendr]` exports live in: `src/rust/init.rs` (`init`),
  `src/rust/core/src/lib.rs` (`silence_panic_output`,
  `find_pharos_config_file`), `src/rust/nonmem/src/model/*.rs` (read/copy/
  summary/lineage/metadata/comment-info/check/run-status),
  `src/rust/nonmem/src/output_files/*.rs` (ext/grd/shk readers, transforms),
  `src/rust/nonmem/src/utils.rs` (config + path helpers),
  `src/rust/scheduler/src/lib.rs` (`submit_model_to_slurm`,
  `submit_model_to_sge`, `get_partition_info`).
- R-side S3/S7 methods: print/knit_print/summary/str for model, summary,
  tree, metadata, audit objects (`R/model-methods.R`, `R/summary-methods.R`,
  `R/tree-methods.R`, `R/metadata-methods.R`, `R/comments-audit.R`).
- Package init: `R/zzz.R` `.onLoad` registers S7 methods, calls
  `silence_panic_output()`, sets default options; `.onAttach` prints a
  config/options status message (`R/utils.R:437-656`).

**Module inventory (one line each).**

R side (~5.3k lines):
- `R/extendr-wrappers.R` (610) — generated Rust bindings; do not hand-edit.
- `R/model-methods.R` (845) — model print/knit/summary dispatch, `$`/`[[`
  masking of `source` tokens, R-side re-derivation of output paths for
  running models (`build_running_summary`, lines 119-183).
- `R/summary-methods.R` (674) — summary display building; loads thresholds
  from pharos config with R-side fallback defaults 0.95/1000 (lines 6-26).
- `R/utils.R` (656) — number formatting, shared table model (console+knit),
  red-flag styling, pharos CLI detection, onAttach message.
- `R/tree-methods.R` (617) — lineage tree/table rendering over Rust lineage
  data; IIFE shadows the extendr `get_model_lineage` to add a `verbose` attr
  (lines 610-617).
- `R/comments-classes.R` (511) — S7 `ThetaComment`/`OmegaComment`/
  `SigmaComment`/`ModelComments`, tracked properties stamping per-field
  provenance ("sources"), validators, `find_parameter()` (lines 347-419).
- `R/comments-query.R` (334) — `resolve_comment()` (lines 56-105) + getters
  (`get_parameter_transform`, `get_eta_labels`, ...).

  resolution with cycle detection, tomledit read-modify-write editors.
- `R/parameter-info.R` (157) — `get_model_parameter_info()`: routes model vs
  run-dir vs .lst input, builds S7 comment objects from Rust
  `get_model_comment_info`.
- `R/comments-audit.R`/`-methods.R`/`-utils.R`/`-fields.R` (~280) — audit

Rust side (~4.7k lines, workspace `hyperion` = crates `core`, `nonmem`,

**Intended layering** (inferred from crate deps and generated wrappers):
R display/UX layer → generated wrappers → hyperion Rust crates → pharos git
crates (parsing, config, NMTRAN, submission). Domain logic is meant to live in
Rust/pharos; R owns presentation and S7 metadata classes. The layering leaks
in both directions: R re-derives filesystem conventions
(`R/model-methods.R:119-183`), and Rust reads R options at runtime
(`core/src/lib.rs:41-56`).

**Most load-bearing files:**
1. `src/rust/nonmem/src/utils.rs` — every read/summary/copy/submit path goes
   through its model-loading + path/config resolution.
2. `R/utils.R` — every print/knit method routes through
   `format_display_data`/`build_display_table_model`.
3. `src/rust/core/src/lib.rs` — error bridge + config-dir discovery used by
   all crates.

**Cross-cutting concerns.**
- Errors: Rust `Result` → `map_to_extendr_err(context)` → R conditions;
  several call sites pass `""` context. One string-sentinel channel:
  `find_pharos_config_file` returns an error *message* as a normal string,
  grepped on the R side (`R/utils.R:563`, `R/pharos-config.R:20`).
- Panics: `.onLoad` installs an empty panic hook (`silence_panic_output`);
  R comments claim "Rust panics abort the R session; tryCatch cannot recover"
  (`R/model-methods.R:123-126`) and guard with `file.exists()` pre-flights.
  ~10 non-test panic/unwrap sites reachable from R (worst:
  `comment_info.rs:125,137`, `ext.rs:95`). (?) actual extendr-0.9 panic
  behavior unverified.
- Config: `pharos.toml` discovered by walking from `hyperion.config_dir`
  option or CWD (Rust); 3 separate loaders in `utils.rs`; summary thresholds
  defaulted in both Rust (`utils.rs:427-459`) and R
  (`R/summary-methods.R:20-23`).
- Logging: none structured; `rprintln!`/cli console output only.
- Concurrency: essentially none (no unsafe, no threads in workspace code).
- Options: 5 `hyperion.*` R options set in `.onLoad`, read ad hoc in display
  code and from Rust.

**Build/test/CI shape.**
- Build: configure → `tools/msrv.R` (checks rustc ≥ 1.65.0 per DESCRIPTION —
  stale vs `edition = "2024"` which needs ≥ 1.85) → `tools/config.R`
  templates Makevars; cargo builds staticlib then runs `cargo run --bin
  document` to regenerate `R/extendr-wrappers.R` during build; git deps need
  network unless a vendor tarball exists (it doesn't; a stale unused
  `src/rust/vendor/` tree sits on disk). (?) vendor-tree deadness inferred
  from `src/Makevars:26-34` activation conditions.
- Tests: 33 testthat files (~1.2k lines), heavily snapshot-based (13 files of
  print/knit snapshots exercising read/summary/lineage end-to-end against
  `inst/extdata` fixtures). Rust unit tests exist only in `utils.rs`,
  `run_status.rs`, `slurm.rs` and are **not run in CI**. Zero tests (R or
  Rust) for submit/init/copy_model/check/metadata-write/use_comments and all
  of ext/grd/shk/transforms/summary/parameters Rust modules.
- CI: R-CMD-check (mac + 4 Ubuntu R versions; Windows row commented out
  despite in-repo Windows scaffolding), daily `pharos-dependency-check`
  tripwire that fails when pharos `main` moves, tag-triggered release
  workflow, PRISM deploy. Pre-commit lefthook: cargo machete/check/fmt,
  roxygen, air/rv fmt.
