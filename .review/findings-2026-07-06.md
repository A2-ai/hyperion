## 1. Architecture summary

hyperion is an R display/metadata layer (S7 + S3 print/knit methods) over a
Rust extendr staticlib (workspace crates `core`, `nonmem`, `scheduler`) that
wraps four pharos git crates. The intended layering — R owns presentation,
Rust/pharos own parsing, path resolution, and submission — is real but leaks
in both directions: R re-derives filesystem conventions and re-walks parsed
model structure for display, and Rust reads R options at runtime
(`core/src/lib.rs:52-56`).

**Spot-check of the addendum map:** verified. All listed entry points,
module sizes, and load-bearing files exist as described. Two `(?)` items
resolved: (a) extendr 0.9's generated wrappers wrap every exported function
in `std::panic::catch_unwind` and convert panics to catchable R errors via
`throw_r_error` (registry source `extendr-macros-0.9.0/src/wrappers.rs:255-284`)
— panics do **not** abort the R session; (b) the stale `src/rust/vendor/`
tree is confirmed dead, and worse: `src/Makevars:26-34` activates offline
mode only for `src/vendor/` or `src/rust/vendor.tar.xz`, neither of which
matches the on-disk `src/rust/vendor/` location, and the release workflow
never builds a vendor tarball.

**Flows traced:** (1) `read_model()` → `load_model_from_input` →
serialized pharos AST → R print pipeline including the omega/sigma block
re-walk; (2) `summary()` on a running model → R-side path guard →
`read_ext_file` → pharos `ExtReader`; (3) `submit_model_to_slurm` →
partition validation → pharos scheduler.

**Refutations (hypotheses from the addendum that did not hold up):**

- **`get_eta_labels` sequence-position labeling is safe.**
  `comment_info::build` (`comment_info.rs:152-180`) walks pharos
  `get_omega_parameters`, which emits an entry for *every* parameter —
  uncommented ones get `Default` info, `BLOCK SAME` blocks are expanded per
  repeat (pharos `parameters.rs::get_block_parameter_names`). Diagonal
  indices are contiguous 1..n in any valid model, so position i == row i.
- **The .ext name join in `get_parameters` is not positional.** pharos
  applies `parameter_names` as a map keyed by the ext file's own coordinate
  names (`param_names.get(&param.name)`), so name/value misalignment cannot
  occur there. The shrinkage join *is* positional
  (count-of-diagonals-so-far indexing into `eta_shrinkage_sd`) but the
  assumption is sound for well-formed ext/shk pairs.
- **`copy_model` does not fully re-implement ext resolution.** It re-derives
  `run_dir`/`stem` inline (`copy.rs:165-181`) but then calls the shared
  `resolve_ext_path`. The duplication is the run-dir convention, not the
  FILE= logic.
- **The wrong ordering in `summary.rs` does not corrupt the parameters
  table.** `compare_parameters` (THETA < SIGMA < OMEGA) is used only to sort
  correlation-matrix rows; the summary parameters table is built by
  partition in THETA→OMEGA→SIGMA order. The defect is real but is a
  display-ordering defect (labels travel with values), not value corruption.

**Overall read:** the Rust core is in decent shape — polymorphic input
resolution is centralized, error mapping is uniform, and pharos does the
hard parsing with per-parameter completeness guarantees. The systemic risk
is concentrated in (a) R-side re-implementations of things pharos already
computes (block structure, output paths, sentinel semantics), which have
already drifted in three verified places, and (b) a test/CI posture that
exercises the display pipeline heavily while never running the Rust tests
or any write path.

Coverage note: vignettes, `grd.rs`, `comments-lookup.R`'s TOML editors, and
`scheduler/src/slurm.rs`'s partition parsing were skimmed or skipped; docs
were checked only where cited.

## 2. Primary findings (ranked)

### F1. Model print silently mislabels omega/sigma parameters for `BLOCK(n) SAME(m)` models

**Severity: High (borderline Critical for IOV-heavy projects) / Category A+D / Confidence: high**

**Evidence:** `R/model-methods.R:548-584`; pharos
`components/nonmem-parser/src/ast.rs:240-241`
(`BlockSame { size: usize, repeats: usize }`, doc: "BLOCK(n) SAME[(m)]:
repeat the previous block `repeats` times"); pharos lowering test for
`SAME(3)` (`lower.rs:2444`); name expansion per repeat in pharos
`parameters.rs::get_block_parameter_names`.

**The issue:** the R block re-walk that builds the printed Omega/Sigma
tables reads `block$structure$BlockSame$size` and **ignores `repeats`**. It
consumes `num_params` names and advances `param_idx` once, while pharos's
name list (the `param_names` vector the walk indexes into,
`model-methods.R:363-367`) contains `size·(size+1)/2 × repeats` entries for
that block. For `$OMEGA BLOCK(1) SAME(5)` — the common IOV shorthand — the
walk consumes 1 name instead of 5, so **every subsequent omega row is
labeled with the wrong coordinate**, and the repeated blocks are not shown
at all. Two adjacent fallback branches are also wrong: a `Block` without
parameters advances by `size` instead of the triangular count
(`model-methods.R:589`), and a `Diagonal` block without parameters advances
by 1 regardless of size (`:592`). Both are currently unreachable (pharos
expands `VALUES(...)` into full parameter lists — verified against the
`everything.mod` snapshot, `_snaps/hyperion-model-print.md:128-137`), but
they will fire if pharos's AST ever gains a sparse form.

**Why tests pass:** every fixture (`iov.mod`, `everything.mod`) writes SAME
blocks as separate records (`repeats = 1`), which the walk handles. The
parseable `SAME(m)` form has zero fixture coverage.

**Blast radius:** wrong parameter labels in the model print/knit tables —
exactly the silently-wrong-labels failure mode the CONTEXT block names as
worst-case. Affects any user model using `SAME(n)` shorthand.

**Remediation sketch:** stop re-walking block structure in R. pharos
already produces the authoritative (name, parameter, block_fixed) list via
`get_omega_parameters` — extend `get_model_comment_info` (or add a sibling
export) to carry initial values/fixed/parametrization per entry, and build
the print table from that. The ~90-line R walk and `create_blocksame_data`
get deleted. Effort: ~1 day. Interim one-line fix: multiply the BlockSame
branch's name consumption and rows by `block$structure$BlockSame$repeats`.

### F2. Panic policy is built on a false premise; the empty panic hook hides the only diagnostics

**Severity: High / Category B / Confidence: high**

**Evidence:** `~/.cargo/registry/.../extendr-macros-0.9.0/src/wrappers.rs:255-284`
(catch_unwind → `throw_r_error`); `src/rust/core/src/lib.rs:58-61`
(`silence_panic_output` installs an empty global panic hook);
`R/zzz.R:3`; `R/model-methods.R:123-126` (comment: "Rust panics abort the R
session; tryCatch cannot recover"); reachable panic sites:
`nonmem/src/model/comment_info.rs:125,137` (`panic!` on pharos invariants),
`nonmem/src/output_files/ext.rs:95` (`table.method.unwrap()`), plus pharos's
own `values[0]` index on torn iteration lines (pharos `ext.rs`, parse loop).

**The issue:** extendr 0.9 converts every panic into a catchable R error.
The R comment claiming the opposite is false, and the `file.exists()`
pre-flight guards it motivates are not load-bearing for session safety
(they *are* load-bearing for F4's silent-empty behavior). The empty panic
hook is a deliberate tradeoff (it prevents the payload printing twice —
see answered Q4), but its cost is that when a panic surfaces, the user
sees only the payload string that reaches `throw_r_error` — for
`ext.rs:95`'s unwrap that is the bare "called `Option::unwrap()` on a
`None` value" with no file, backtrace, or context — which is why the panic
sites themselves must become `Result`s. The `method` field is `None`
whenever pharos does not recognize the method text on a `TABLE NO.` line
(new/unusual NONMEM methods), so this is reachable from `read_ext_file` on
real files.

**Blast radius:** every future maintainer decision about error handling at
the boundary is being made against a wrong model of the runtime; users get
context-free errors on exotic inputs.

**Remediation sketch:** document the real policy (panics = catchable R
errors) where the wrong comment sits; replace the two `panic!`s and the
`unwrap()` with `Result` + `map_to_extendr_err` (mechanical, < 1 hour).
The empty panic hook itself stays: maintainer confirms it is essential to
prevent a double panic message (the default hook prints the payload to
stderr, and extendr then rethrows the same payload as the R error) — add a
comment saying so at `core/src/lib.rs:58-61` so the next reviewer doesn't
re-litigate it. Effort: hours.

### F3. `$EST FILE=` and run-dir conventions resolved differently in R and Rust; running-model summary silently empty

**Severity: High / Category D / Confidence: high**

**Evidence:** `src/rust/nonmem/src/utils.rs:200-211` (`resolve_ext_path`
honors `$EST FILE=` inheritance); `R/model-methods.R:126-155`
(`build_running_summary` re-derives `{dir}/{stem}/{stem}.ext|.grd` by naive
convention and gates the Rust call on `file.exists()` of that path);
pharos `get_summary` honors FILE= via `resolve_estimation_files`
(pharos `output_files/mod.rs:140`); `copy.rs:143-156` (`to` used raw from
CWD while a model-object `from` resolves config-relative via
`extract_model_source` → `from_config_relative`, `utils.rs:290-312`).

**The issue:** for a **running** model that uses `$EST FILE=custom.ext`,
the conventional `{stem}.ext` does not exist, so the guard skips the read
and `summary()` prints a running summary with no iterations — silently,
with no hint that data exists. (Completed-run summaries are correct because
both pharos and hyperion's Rust honor FILE=.) The guard exists only because
of the false panic premise (F2). Separately, `copy_model(model_obj,
"run002.mod")` mixes path bases in one call: `from` is config-relative,
`to` is CWD-relative, so running it from a subdirectory writes the copy
somewhere other than beside its parent model.

**Blast radius:** silent missing data when monitoring long runs (the exact
moment users care); copies landing in unexpected directories in scripted
workflows.

**Remediation sketch:** delete the R-side path derivation; expose one Rust
entry point ("resolve expected output files for this model") and let
`build_running_summary` call Rust unconditionally, treating error returns
as "not available yet" (safe now per F2). Decide and document one base for
`copy_model`'s `to` (config-relative to match `from` would be consistent).
Effort: half a day.

### F4. Test and CI coverage anti-correlated with risk; Rust tests never run in CI

**Severity: High / Category E / Confidence: high**

**Evidence:** `.github/workflows/R-CMD-check.yaml` (no `cargo test` step);
`lefthook.yaml` (machete/check/fmt only); existing `#[test]`s in
`utils.rs:529-687`, `run_status.rs:109-163`, `scheduler/src/slurm.rs` are
therefore never executed anywhere; grep of `tests/testthat/` shows zero
calls to `copy_model`, `init`, `check_model`, `submit_model_to_*`,
`set/update/clear_metadata_file`, `use_comments`; ext/grd/shk/transforms/
summary/parameters Rust modules have no tests at all; fixture gap for
`SAME(m)` is what let F1 survive the otherwise-thorough snapshot suite.

**The issue:** the 13 snapshot files exercise the display pipeline
end-to-end (genuinely good), but nothing exercises any state-mutating path
or any line of the hand-rolled .ext/.shk interpretation, and the Rust tests
that do exist are dead weight in CI — they can silently rot or silently
pass-if-run-never.

**Blast radius:** the highest-risk code (sentinel parsing, metadata writes,
copy) regresses invisibly; contributors get no signal.

**Remediation sketch:** (1) add a `cargo test --manifest-path src/rust/Cargo.toml`
step to R-CMD-check and lefthook — hours, immediate payoff; (2) unit tests
for `fix_parameter_values`/`get_final_estimates` against the shipped exotic
fixtures (`inst/extdata/ext/itsimp.ext`, `bql.ext`) and a `SAME(3)` model
fixture asserting print labels; (3) tmpdir round-trips for
`copy_model` and metadata write/clear. Effort: 2–3 days total, incremental.

### F5. .ext sentinel-row semantics implemented twice (hyperion + pharos) and already drifted

**Severity: Medium / Category A / Confidence: high**

**Evidence:** hyperion `ext.rs:174-222` (`fix_parameter_values`: fixed iff
the `-1000000006` row value `== 1.0`, applied only when **both** the
`-1000000006` and `-1000000001` rows are present); pharos
`extract_parameters_from_table` (fixed iff `v == 1.0 || |v| == 1e10`;
stderr additionally filtered for `0.0` and `1e10`).

**The issue:** `read_ext_file` (hyperion's interpretation) and
`get_parameters` (pharos's interpretation) can disagree about the same file.
Concretely: when the fixed-flags row is absent or a fixed parameter is
marked `1e10`, `read_ext_file` output retains NONMEM's `1.0E+10`
placeholder standard errors as if they were data, and the NaN→NA conversion
is also skipped entirely because it lives inside the both-rows-present
branch (`ext.rs:185`). pharos filters those same values out.

**Blast radius:** anyone post-processing `read_ext_file` output (the
documented workflow for custom tables) can ingest 1e10 as a real SE — a
silently-wrong number in a report.

**Remediation sketch:** make pharos's interpretation the single one — have
`read_ext_file` delegate sentinel handling to pharos (or extract one shared
function in hyperion used by both paths), and hoist NaN→NA out of the
sentinel branch. Effort: half a day + tests from F4.

### F6. `get_final_estimates` assumes homogeneous schemas across files; mismatches are silently misattributed or dropped

**Severity: Medium / Category D / Confidence: high**

**Evidence:** `ext.rs:343-355` (parameter names taken from the first file
only, comment admits "all should be the same"); `ext.rs:373-377` (silent
`if param_idx < param_columns.len()` bound drops extra values);
ragged shorter rows leave columns of unequal length feeding
`data_frame!` (`ext.rs:387-395`); `ext.rs:362-364` (`tables.first()` means
the `only_last = FALSE` parameter is accepted and then ignored).

**The issue:** the documented use ("bootstrap/" directory scans, recursive)
makes heterogeneous inputs likely — one stray run with a different model in
the tree and either (a) same column count, different meaning: values land
under the wrong parameter names with no warning, or (b) different count:
extra columns silently vanish / short columns produce a malformed
data.frame.

**Blast radius:** bootstrap/scan summaries with misattributed estimates.

**Remediation sketch:** compare each file's header names to the first;
error (or fill by name with NA) on mismatch, and honor or reject
`only_last = FALSE`. ~30 lines. Effort: hours.

### F7. Two R name resolvers with divergent matching semantics; the query path silently returns the first ambiguous match

**Severity: Medium / Category A / Confidence: high**

**Evidence:** `find_parameter` (`R/comments-classes.R:347-419`): matches
key, `@name`, `@display`; aborts on any ambiguity, including within a kind.
`resolve_comment` (`R/comments-query.R:56-105`): strips a `" (...)"` suffix,
matches key, `@name`, and omega `@raw_name` (not `@display`); returns the
**first** match within a kind with no ambiguity detection.

**The issue:** the same user-facing name string resolves differently
depending on which API is called. Two omegas sharing a raw `@name` (e.g.
two "IIV" comments): `get_parameter_transform(mc, "IIV")` silently returns
the first one's transform — feeding a potentially wrong CV/CI into a report
— while `update_parameter(mc, "IIV", ...)` aborts as ambiguous. A display
name works in the update path but returns NA from the query path;
`"OM1 (CL)"` works in the query path but not the update path.

**Blast radius:** wrong transform/unit silently attached to a parameter in
derived quantities; user-visible API inconsistency that generates support
questions.

**Remediation sketch:** collapse to one resolver (find_parameter's
collect-then-check shape, extended with raw_name and suffix-stripping),
with the ambiguity abort everywhere. Effort: hours; snapshot review needed.

### F8. Config plumbing: three loaders, three failure semantics; malformed pharos.toml silently erases all parameter names; thresholds defaulted in three places

**Severity: Medium / Category E / Confidence: high**

**Evidence:** `utils.rs:373-380` (`get_comment_type` returns `None` on
*any* failure — missing config, unreadable file, TOML syntax error — with
no warning); `utils.rs:382-414` (`load_nonmem_config` falls back to a bare
CWD join, a third discovery convention); `utils.rs:427-459`
(`get_pharos_config` errors loudly when config is missing but silently
reduces the whole config to two thresholds, defaulting them `0.95`/`1000.0`
in Rust); `R/summary-methods.R:6-26` (same two defaults duplicated in R);
`R/zzz.R:15-21` (rse/shrinkage thresholds live in a fourth channel, R
options); string-sentinel error channels: `core/src/lib.rs:64-74` returns
an error *sentence* as a normal string, grepped at `R/utils.R:563` and
`R/pharos-config.R:20`; `check.rs:37-39` greps `"NMTRAN.exe not found"` out
of an error string and converts it to exit code `-1`, conflating it with
NMTRAN's own codes.

**The issue:** a typo'd `pharos.toml` makes every parameter name silently
disappear from every table (comment_type → None → pharos returns raw
coordinates) with zero diagnostics — indistinguishable from "no comments
written". The threshold defaults have no single source of truth: changing
the pharos default changes summary behavior only for users whose config
loads, while the R and Rust fallbacks pin old values. The sentinel strings
mean a wording change in `core` silently flips both R call sites into the
"config found" branch, after which `use_comments` tries to parse the error
message as a TOML file path.

**Remediation sketch:** one config accessor in Rust returning a typed
result distinguishing absent / malformed / loaded (warn R-side on
malformed); make `find_pharos_config_file` return NULL or a condition
instead of prose; define thresholds once (pharos config crate) and delete
the R and Rust literal fallbacks. Effort: ~1 day.

### F9. Canonical parameter ordering implemented twice in Rust with confirmed drift (correlation matrix violates THETA < OMEGA < SIGMA)

**Severity: Medium / Category A / Confidence: high**

**Evidence:** `summary.rs:78-126` (`parse_parameter_for_ordering` +
`compare_parameters`: THETA=0, SIGMA=1, OMEGA=2) vs `parameters.rs:26-81`
(`extract_param_sort_key` + `compare_param_names`: THETA=0, OMEGA=1,
SIGMA=2 — the convention the maintainer confirmed as canonical). The two
comparators also disagree on unknown-name placement (`255, vec![]` vs
`(u32::MAX, u32::MAX, 3)`) and index-parse failure (`unwrap_or(0)` sorts
unparseable names first vs last).

**The issue:** `compare_parameters` orders the correlation-matrix rows in
summary output SIGMA-before-OMEGA, contrary to convention and to every
other table in the package. Because labels travel with values this is a
display-ordering defect, not data corruption — but it is a
maintainer-confirmed wrong ordering shipping in report output today, and
the duplicate comparator is how it happened.

**Blast radius:** inconsistent parameter order between the correlation
section and the parameters section of the same summary; report reviewers
reading by position.

**Remediation sketch:** delete `parse_parameter_for_ordering` /
`compare_parameters` and use `compare_param_names` (already `pub(crate)`)
in `build_correlation_matrix_df`. ~20-line diff; correlation snapshots will
change (maintainer accepts snapshot diffs themselves). Effort: < 1 hour.

## 4. Questions for maintainers — answered 2026-07-08

1. The `init()` example (`init.rs:23`) creates
   `model/nonmem/submission-log/pharos.toml`, which CWD-walk discovery can
   never find from the project root.
   **Answer: the example is wrong.** Fix the roxygen example to create
   `pharos.toml` at the project root (added to low-hanging fruit below).
2. `get_run_status` reports `not_run` when the run dir exists without a
   `.lst` (`run_status.rs:41-43`) — a queued-but-not-started cluster job
   shows as never-run.
   **Answer: acceptable as-is.** No fourth state wanted. Carry to the next
   addendum's known-intentional list.
3. `hide_off_diagonal_params` docs say "will not display the unfixed
   off-diagonal" but pharos's include rule (`diagonal || (!fixed &&
   !hide)`) means *fixed* off-diagonals are never shown regardless of the
   flag.
   **Answer: intended.** NONMEM's .ext lists the full lower triangle,
   including structural zeros for covariances that were never modeled, and
   marks them fixed (the `-1000000006` row). Always hiding fixed
   off-diagonals keeps output from flooding with `ETA2:ETA1 = 0` rows; the
   flag governs only *estimated* off-diagonals. Optionally clarify in the
   roxygen that fixed off-diagonals are never shown. Carry to the next
   addendum's known-intentional list.
4. The empty panic hook is global for the R session — any remaining reason
   to keep it, given extendr already converts panics to R errors?
   **Answer: keep it — essential.** It prevents a double panic message:
   the default hook prints the payload to stderr and extendr then rethrows
   the same payload as the R error. F2's remediation sketch has been
   updated accordingly (fix the wrong comment and the panic sites, not the
   hook). Carry to the next addendum's known-intentional list.

## 5. What's good

- **Centralized polymorphic input resolution.** Nearly every Rust entry
  point routes through `load_model_from_input`/`path_from_robj`
  (`utils.rs:104-198`, with documented edge-case handling for in-run-dir
  files). This is the right shape — F3's fix is to route the last two
  stragglers (R's running-summary guard, copy_model's `to`) through it, not
  to change it.
- **pharos as the single parsing authority actually holds.**
  `comment_info::build` walks pharos's per-parameter iteration, which emits
  complete, repeat-expanded, off-diagonal-inclusive entries; the ext name
  join is map-keyed. The invariant "R never re-parses NONMEM" is respected
  — the residual risk is R re-walking *structure*, not re-parsing text.
- **Intent is written down where it matters.** The lineage `filter_lineage`
  workaround, the extendr NULL-default quirk (`lineage.rs:120-123`), the
  test config-dir pinning, and the deliberate `based_on` edge-dropping all
  carry comments explaining *why* — this review could suppress several
  false positives purely from in-repo rationale. Preserve that habit.
- **The snapshot suite is a real end-to-end harness.** `everything.mod`
  plus the exotic ext fixtures exercise the full read→parse→render pipeline
  cheaply; extending it with a `SAME(m)` fixture and running `cargo test`
  in CI (F4) leverages infrastructure that already exists rather than
  building new.
