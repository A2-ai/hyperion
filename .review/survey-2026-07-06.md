## 1. Repository map

**Purpose.** hyperion is an R package companion to the `pharos` CLI for
pharmaceutical (NONMEM) model development: read/validate/copy models, submit
them to SLURM/SGE clusters, summarize runs, extract parameter estimates and
structured parameter metadata, and track model lineage. Codebase type: **R
library (S7/S3) over a Rust staticlib backend (extendr)**, which itself wraps
four pharos git crates. First supported modeling software is NONMEM.

**Entry points.**
- No mains/routes. Public surface = ~60 R exports (`NAMESPACE`), of which 37
  are thin `.Call` wrappers generated into `R/extendr-wrappers.R` at build time
  by `src/rust/document.rs`.
- Rust `#[extendr]` exports live in: `src/rust/init.rs` (`init`),
  `src/rust/core/src/lib.rs` (`silence_panic_output`,
  `find_pharos_config_file`), `src/rust/nonmem/src/model/*.rs` (read/copy/
  summary/lineage/metadata/comment-info/check/run-status),
  `src/rust/nonmem/src/output_files/*.rs` (ext/grd/shk readers, transforms),
  `src/rust/nonmem/src/utils.rs` (config + path helpers),
  `src/rust/scheduler/src/lib.rs` (`submit_model_to_slurm`,
  `submit_model_to_sge`, `get_partition_info`).
- R-side S3/S7 methods: print/knit_print/summary/str for model, summary,
  tree, metadata, audit objects (`R/model-methods.R`, `R/summary-methods.R`,
  `R/tree-methods.R`, `R/metadata-methods.R`, `R/comments-audit.R`).
- Package init: `R/zzz.R` `.onLoad` registers S7 methods, calls
  `silence_panic_output()`, sets default options; `.onAttach` prints a
  config/options status message (`R/utils.R:437-656`).

**Module inventory (one line each).**

- `R/tree-methods.R` (617) — lineage tree/table rendering over Rust lineage

**Intended layering** (inferred from crate deps and generated wrappers):
R display/UX layer → generated wrappers → hyperion Rust crates → pharos git
crates (parsing, config, NMTRAN, submission). Domain logic is meant to live in
Rust/pharos; R owns presentation and S7 metadata classes. The layering leaks
in both directions: R re-derives filesystem conventions
(`R/model-methods.R:119-183`), and Rust reads R options at runtime
(`core/src/lib.rs:41-56`).

**Most load-bearing files:**
1. `src/rust/nonmem/src/utils.rs` — every read/summary/copy/submit path goes
   through its model-loading + path/config resolution.
2. `R/utils.R` — every print/knit method routes through
   `format_display_data`/`build_display_table_model`.
3. `src/rust/core/src/lib.rs` — error bridge + config-dir discovery used by
   all crates.

**Cross-cutting concerns.**
- Errors: Rust `Result` → `map_to_extendr_err(context)` → R conditions;
  several call sites pass `""` context. One string-sentinel channel:
  `find_pharos_config_file` returns an error *message* as a normal string,
  grepped on the R side (`R/utils.R:563`, `R/pharos-config.R:20`).
- Panics: `.onLoad` installs an empty panic hook (`silence_panic_output`);
  R comments claim "Rust panics abort the R session; tryCatch cannot recover"
  (`R/model-methods.R:123-126`) and guard with `file.exists()` pre-flights.
  ~10 non-test panic/unwrap sites reachable from R (worst:
  `comment_info.rs:125,137`, `ext.rs:95`). (?) actual extendr-0.9 panic
  behavior unverified.
- Config: `pharos.toml` discovered by walking from `hyperion.config_dir`
  option or CWD (Rust); 3 separate loaders in `utils.rs`; summary thresholds
  defaulted in both Rust (`utils.rs:427-459`) and R
  (`R/summary-methods.R:20-23`).
- Logging: none structured; `rprintln!`/cli console output only.
- Concurrency: essentially none (no unsafe, no threads in workspace code).
- Options: 5 `hyperion.*` R options set in `.onLoad`, read ad hoc in display
  code and from Rust.

**Build/test/CI shape.**
- Build: configure → `tools/msrv.R` (checks rustc ≥ 1.65.0 per DESCRIPTION —
  stale vs `edition = "2024"` which needs ≥ 1.85) → `tools/config.R`
  templates Makevars; cargo builds staticlib then runs `cargo run --bin
  document` to regenerate `R/extendr-wrappers.R` during build; git deps need
  network unless a vendor tarball exists (it doesn't; a stale unused
  `src/rust/vendor/` tree sits on disk).
- Tests: 33 testthat files (~1.2k lines), heavily snapshot-based (13 files of
  print/knit snapshots exercising read/summary/lineage end-to-end against
  `inst/extdata` fixtures). Rust unit tests exist only in `utils.rs`,
  `run_status.rs`, `slurm.rs` and are **not run in CI**. Zero tests (R or
  Rust) for submit/init/copy_model/check/metadata-write/use_comments and all
  of ext/grd/shk/transforms/summary/parameters Rust modules.
- CI: R-CMD-check (mac + 4 Ubuntu R versions; Windows row commented out
  despite in-repo Windows scaffolding), daily `pharos-dependency-check`
  tripwire that fails when pharos `main` moves, tag-triggered release
  workflow, PRISM deploy. Pre-commit lefthook: cargo machete/check/fmt,
  roxygen, air/rv fmt.

## 2. Risk hypotheses (ranked, max 8)

### H1 — Parameter identity/ordering is implemented ≥4 times and has already drifted
- **Hypothesis:** The mapping "which estimate belongs to which parameter
  name/label, in what order" is independently implemented in at least four
  places, and two Rust copies already disagree, so user-facing tables can
  mislabel or misorder estimates.
- **Signal:** `src/rust/nonmem/src/model/summary.rs:80-97` orders
  THETA < SIGMA < OMEGA while `src/rust/nonmem/src/model/parameters.rs:26-60`
  orders THETA < OMEGA < SIGMA; both hand-parse `NAME(i,j)` indices
  (summary.rs:100-111, parameters.rs:45-58). R re-walks omega/sigma block
  structure with a manual `param_idx` to align names
  (`R/model-methods.R:510-606`, incl. BlockSame back-search). A fourth
  R-side layer resolves names two different ways: `find_parameter()`
  (`R/comments-classes.R:347-419`) vs `resolve_comment()`
  (`R/comments-query.R:56-105`) with different match fields (display vs
  raw_name, suffix-stripping).
- **If true, cost:** wrong parameter labels/ordering in scientific reporting
  output — the highest-severity failure class this package can have.
- **Investigation sketch:** diff the two Rust sort keys and determine which
  ordering the .ext/.shk join in `get_parameters` (parameters.rs:103-200)
  actually requires; construct/inspect a model with non-contiguous omega
  diagonals + BlockSame (`inst/extdata/mod/everything.mod`,
  `iov.mod`) and trace name alignment through
  `get_model_parameter_names` → `get_random_effect_parameter_data`; compare
  `find_parameter` vs `resolve_comment` match semantics for the same query
  strings; check `get_eta_labels` (`R/comments-query.R:291-334`) labeling by
  sequence position vs omega row index.
- **Confidence:** high.

### H2 — Panic policy at the extendr boundary is incoherent and undertested
- **Hypothesis:** The codebase simultaneously believes panics abort the R
  session (guards + comments), silences panic output globally, and leaves
  panic paths reachable from exported functions — at least one of these is
  wrong, and whichever it is, error UX on malformed inputs is broken.
- **Signal:** empty panic hook installed at load
  (`src/rust/core/src/lib.rs:58-61`, called from `R/zzz.R:3`); comment
  "Rust panics abort the R session; tryCatch cannot recover"
  (`R/model-methods.R:123-126`) motivating `file.exists()` pre-flight
  guards; reachable panics: `panic!` in
  `nonmem/src/model/comment_info.rs:125,137`, `unwrap()` on `table.method`
  in `nonmem/src/output_files/ext.rs:95`.
- **If true, cost:** either aborted user R sessions on malformed NONMEM
  outputs, or silently swallowed diagnostics (empty hook) — both bad for an
  interactive scientific tool.
- **Investigation sketch:** establish what extendr 0.9 actually does on
  unwind (catch → R error vs abort), then audit each reachable
  panic/unwrap; test `read_ext_file` on an ext table missing a method line
  and `get_model_comment_info` on mismatched omega comments; decide the de
  facto policy and where the guards are load-bearing.
- **Confidence:** high.

### H3 — Output-file location logic is split R/Rust with convention drift ($EST FILE= only honored on the Rust path)
- **Hypothesis:** Rust owns `$EST FILE=`-aware ext resolution
  (`resolve_ext_path`) but R re-derives `{dir}/{stem}/{stem}.ext|.grd` by
  string convention for running models, and `copy_model` re-implements the
  same resolution inline with a different path base — so the three paths can
  disagree about which file to read.
- **Signal:** `R/model-methods.R:119-170` (`build_running_summary`) builds
  `ext_path`/`grd_path` by naive convention as a panic guard;
  `src/rust/nonmem/src/utils.rs:206-211` (`resolve_ext_path`) honors
  `$EST FILE=`; `src/rust/nonmem/src/model/copy.rs:165-196` duplicates
  run-dir/ext resolution inline and takes the `to` path raw from CWD while
  other paths are config-relative (`utils.rs:274-301`). NEWS 0.5.0 documents
  the `$EST FILE=` fix for four functions — the R-side guard predates/escapes
  it.
- **If true, cost:** running-model summaries silently show "no iteration data"
  (or stale data) for models using `$EST FILE=`; copy/update reads estimates
  from the wrong place when CWD ≠ config dir.
- **Investigation sketch:** trace `summary()` on a running model whose
  `$EST` uses `FILE=`; grep all R-side `file.path(dirname(...),
  base_name, ...)` constructions and map each to its Rust counterpart; check
  `from_config_relative`/`to_config_relative` fallback behavior
  (`utils.rs:279-301`) when canonicalize fails or config dir is absent;
  verify `copy_model`'s `to` handling from a subdirectory.
- **Confidence:** high.

### H4 — Hand-rolled .ext parsing has silent-wrong-data modes and zero tests
- **Hypothesis:** `ext.rs` parses NONMEM .ext files with hardcoded sentinel
  codes and positional column filling; edge cases (missing sentinel rows,
  heterogeneous multi-table files) produce silently wrong dataframes rather
  than errors.
- **Signal:** sentinel iteration codes -1000000006/-1000000001 handled only
  when *both* present (`src/rust/nonmem/src/output_files/ext.rs:182-221`);
  final-estimate rows selected by string prefix "-1000000000" (ext.rs:294);
  `get_final_estimates` takes parameter names from the first file only and
  tolerates row-length mismatches silently (ext.rs:343-376). Zero tests in
  ext.rs; fixtures for exotic methods exist unexercised
  (`inst/extdata/ext/itsimp.ext`, `saemimp.lst`, `bql.ext`).
- **If true, cost:** wrong estimates/SEs attributed to wrong parameters in
  returned dataframes — silent scientific error.
- **Investigation sketch:** run `read_ext_file`/`get_final_estimates` against
  the shipped exotic fixtures; construct an ext with a fixed-flag row but no
  SE row (and vice versa); two models with different parameter sets under one
  root for `get_final_estimates`; check the shk join in
  `get_parameters` (parameters.rs:103-200) for the same class of positional
  assumptions (and shk.rs eta/eps near-duplication, shk.rs:57-218).
- **Confidence:** medium-high.

### H5 — Test coverage is anti-correlated with risk; Rust tests never run in CI
- **Hypothesis:** The tested surface (print/knit snapshots, comment classes)
  is the low-risk display layer, while every side-effectful or numerical
  path (submit, init, copy_model, check, metadata writes, ext/grd/shk/
  transforms parsing) has no direct tests; existing Rust unit tests don't run
  in CI at all.
- **Signal:** 13/33 test files are snapshots of print/knit; no test invokes
  `copy_model`, `init`, `check_model`, `submit_model_to_*`,
  `set/update/clear_metadata_file`, `use_comments` (tests/testthat/ inventory);
  `#[test]`s exist only in `utils.rs`/`run_status.rs`/`slurm.rs`;
  `.github/workflows/R-CMD-check.yaml` never runs `cargo test`; lefthook runs
  cargo check/fmt but not test.
- **If true, cost:** regressions in the highest-risk code ship undetected;
  Rust tests rot.
- **Investigation sketch:** confirm the coverage map; identify the 3-4
  cheapest high-value seams (copy_model round-trip on tmpdir fixtures,
  metadata write/clear round-trip, ext parsing unit tests, `cargo test` CI
  step) and verify nothing structural blocks them (e.g., NMTRAN/cluster
  dependencies are isolated to check.rs/scheduler only).
- **Confidence:** high (that the gap exists); medium (that it hides live bugs).

### H6 — Dependency/version skew: pharos `main` tracking, stale vendor tree, stale MSRV
- **Hypothesis:** Reproducibility and version coherence ride entirely on
  Cargo.lock while multiple declared versions have already drifted.
- **Signal:** all four pharos crates pinned to `branch = "main"`
  (`src/rust/Cargo.toml`); daily CI tripwire fails whenever pharos main moves
  (`.github/workflows/pharos-dependency-check.yaml`); `Config/PharosVersion:
  0.5.1` in DESCRIPTION vs main-tracking deps; stale unused
  `src/rust/vendor/` tree on disk (Makevars vendoring never activates —
  `src/Makevars:26-34`); DESCRIPTION `rustc >= 1.65.0` vs `edition = "2024"`
  (needs ≥ 1.85); git history is dominated by "update pharos" commits.
- **If true, cost:** unreproducible source builds, confusing version errors
  for users, CI red-X noise training people to ignore failures.
- **Investigation sketch:** verify vendor/ is truly dead and whether shipping
  it bloats the package; check what a user building from source without the
  pharos-repo token experiences; confirm msrv.R vs real MSRV; assess whether
  `Config/PharosVersion` (used by the onAttach version check,
  `R/utils.R:492-497`) can disagree with the linked crate versions.
- **Confidence:** medium (parts may be intentional co-development workflow).

### H7 — Config plumbing: string-sentinel errors and duplicated defaults
- **Hypothesis:** Config discovery/loading has three Rust loaders, one
  string-typed error channel, and thresholds defaulted independently in Rust
  and R — the pieces can disagree silently.
- **Signal:** `find_pharos_config_file` returns an error message as a normal
  string (`core/src/lib.rs:64-74`), grepped in `R/utils.R:563` and
  `R/pharos-config.R:20`; `get_pharos_config` hand-builds only two summary
  thresholds with baked defaults 0.95/1000 (`nonmem/src/utils.rs:427-459`)
  duplicated in `R/summary-methods.R:20-23`; `get_comment_type` returns
  silent None on any config failure (`utils.rs:373-380`);
  `load_nonmem_config` falls back to CWD (`utils.rs:388`).
- **If true, cost:** wording change breaks missing-config detection; users
  with a malformed pharos.toml silently get type-default comment parsing and
  default thresholds with no warning.
- **Investigation sketch:** enumerate the three loaders' failure behaviors
  against a malformed/missing/mislocated pharos.toml; check whether
  `use_comments()` can write a config that `get_comment_type` then silently
  ignores.
- **Confidence:** medium.

### H8 — Scheduler asymmetry: SGE path lacks the validation/UX the SLURM path has
- **Hypothesis:** `submit_model_to_sge` skips partition/queue validation and
  advice that the SLURM path performs, so SGE failures surface as raw pharos
  errors after submission rather than pre-flight guidance.
- **Signal:** slurm partition check + R-level `stop`/`warning` advice at
  `src/rust/scheduler/src/lib.rs:133-150`; SGE path (235-296) has no
  equivalent; `get_partition_info` is slurm-only
  (`scheduler/src/slurm.rs:190-197`). No tests for either submit path.
- **If true, cost:** degraded UX/errors for SGE users; asymmetric behavior
  documented nowhere.
- **Investigation sketch:** compare the two submit functions end-to-end
  (env handling, verbose flag, pharos invocation args); determine whether SGE
  offers an equivalent to partition info that was skipped deliberately.
- **Confidence:** medium-low.

## 3. Questions for the maintainer (max 10)

Each with the default assumption applied if unanswered.

- **Q1 → H1.** `summary.rs` orders parameters THETA < SIGMA < OMEGA
  (summary.rs:80-97) while `parameters.rs` orders THETA < OMEGA < SIGMA
  (parameters.rs:26-60). Intentional display-vs-data convention, or drift?
  *Default: drift — review as a correctness risk.*
- **Q2 → H2.** `.onLoad` silences all Rust panic output, and comments claim
  panics abort the R session. Is crash-on-panic (with no message) the
  accepted policy for malformed NONMEM outputs, or legacy belief?
  *Default: not accepted — panic paths reachable from R are defects.*
- **Q3 → H6.** pharos crates track `branch = "main"` with Cargo.lock as the
  real pin, plus a daily drift-tripwire CI job. Is this the deliberate
  co-development workflow? *Default: yes, intentional — review only its
  reproducibility edges (vendor tree, token-less builds), not the choice
  itself.*
- **Q4 → H3.** Can users point hyperion at NONMEM runs *not* produced by
  pharos submission scripts (different output layout, `$EST FILE=` usage)?
  *Default: yes — R-side `{stem}/{stem}.ext` convention derivation is a real
  risk, not a guaranteed invariant.*
- **Q5 → H5.** Is the untested surface (submit, init, copy_model, check,
  metadata writes) accepted as manually-tested because it needs
  NMTRAN/cluster? *Default: the cluster/NMTRAN boundary is accepted;
  copy_model/metadata/ext-parsing having no tests is not.*
- **Q6 → H8.** Is SGE partition validation parity planned, or is SGE a
  second-class target? *Default: asymmetry is accidental.*
- **Q7 → targeting.** Which matters more right now: correctness of displayed
  estimates/labels (H1/H4) or robustness of the submission/config workflow
  (H3/H7/H8)? *Default: correctness of displayed numbers.*
- **Q8 → H6.** Windows: configure.win/Makevars.win.in/conjurer-win.def exist
  but the CI matrix row is commented out. Supported target or aspirational?
  *Default: aspirational — don't review Windows-specific code paths except as
  rot risk.*
- **Q9 → parking lot.** `inst/lookup.toml` ships `parameterization = "Corr"`
  and `"Stdev"`, which are not in `valid_parameterizations()`
  (R/comments-fields.R) and appear to be silently dropped when applied
  (R/comments-lookup.R:104-109). Planned vocabulary or bug in the example?
  *Default: bug in the shipped example.*
- **Q10 → H4.** Do multi-method runs (SAEM+IMP, ITS+IMP — fixtures
  `inst/extdata/ext/itsimp.ext`, `saemimp.lst` exist) occur routinely for
  your users? *Default: yes — heterogeneous .ext tables are in scope for the
  parsing review.*

### Addendum summary (full text in the addendum file)

- **CONTEXT**: hyperion = R display/metadata layer over Rust extendr backend
  over pharos git crates; consumers are pharmacometricians producing
  scientific reports, so silently-wrong numbers/labels are the worst-case
  failure. Known-intentional up front: pharos owns comment parsing (NA names
  OK); pharos deps track `main` with Cargo.lock as pin `[Q3]`; snapshots are
  maintainer-owned.
- **PRIORITY TARGETS** (~80% effort):
  - T1 `[Q1]` — parameter identity/ordering implemented ≥4×, Rust copies
    already disagree (summary.rs:80-97 vs parameters.rs:26-60; R block walk
    `R/model-methods.R:510-606`; `find_parameter` vs `resolve_comment`).
  - T2 `[Q2]` — panic policy at the extendr boundary (empty panic hook,
    "panics abort session" comments, reachable `panic!`/`unwrap` in
    comment_info.rs:125,137 and ext.rs:95).
  - T3 `[Q4]` — output-file location split R/Rust; `$EST FILE=` honored only
    on the Rust path (`utils.rs:206-211` vs `R/model-methods.R:119-170`;
    copy.rs:165-196 mixed path bases).
  - T4 `[Q10]` — hand-rolled .ext parsing silent-wrong-data modes, zero
    tests (ext.rs:182-221, 294, 343-376; shk.rs:57-218).
  - T5 `[Q5]` — test coverage anti-correlated with risk; Rust tests never
    run in CI.
- **OPEN HUNT** (~20%): config-loader failure modes + string-sentinel error
  channel; metadata.rs write paths; transforms.rs numerics; scheduler
  SLURM/SGE asymmetry `[Q6]`; lineage filter + tree regex-on-rendering;
  vignettes/docs vs behavior; Windows scaffolding rot `[Q8]`.
- **KNOWN-INTENTIONAL / OUT OF SCOPE**: pharos owns parsing (maintainer
  instruction + NEWS 0.5.0); snapshots maintainer-owned (maintainer
  instruction); pharos `main`-tracking workflow `[Q3]` (workflow file +
  README badge); test config-dir pinning (in-repo comment in
